# Справочник API

Базовый адрес локального Compose: `http://127.0.0.1:8081`.

## Общие правила

- JSON-запросы содержат ровно один объект. Неизвестные поля и дополнительные JSON-значения отклоняются.
- Максимальный размер тела — 64 KiB. Лимиты строк ниже указаны в **байтах UTF-8**, не в количестве символов.
- NUL (`\u0000`) в имени, заголовке и описании запрещён: PostgreSQL `TEXT` его не поддерживает.
- Даты ответов — RFC 3339 с часовым поясом; в примерах не фиксируются вымышленные результаты.
- Ошибки обработчиков: `{"error":"message"}`. Неизвестный маршрут и неподдерживаемый метод обрабатываются стандартным `ServeMux`: `404`/`405` с текстовым телом.
- Ответы помечены `Cache-Control: no-store`. Пароль и его hash не возвращаются.
- `GET`-маршруты также поддерживают `HEAD` по стандартным правилам `net/http`.

## Регистрация

`POST /api/v1/auth/register`, без токена:

```json
{"email":"timur@example.com","name":"Timur","password":"local-demo-password"}
```

| Поле | Правила |
|---|---|
| `email` | Email без display name, до 254 байт; края обрезаются, адрес переводится в lowercase |
| `name` | 1–80 байт после обрезки пробельных краёв |
| `password` | 12–72 байта; пробелы не удаляются |

`201 Created`: объект пользователя с полями `id`, `email`, `name`, `created_at`. Пароль хешируется bcrypt с default cost 10. Ограничение 72 байта исключает неявное усечение bcrypt. Проверки доставляемости адреса нет.

Ошибки: `400` — поля невалидны, `409` — email уже зарегистрирован, `413` — слишком большое тело.

## Вход

`POST /api/v1/auth/login`, без токена:

```json
{"email":"timur@example.com","password":"local-demo-password"}
```

`200 OK`:

```json
{"access_token":"<signed-jwt>","token_type":"Bearer"}
```

Access-токен действует один час. JWT подписывается HS256; проверяются алгоритм, подпись, обязательные `exp`, `iss`, `aud` и положительный числовой `sub`; `iat` и `nbf` проверяются при наличии. Содержимое JWT можно прочитать без секрета: токен не зашифрован.

Неверный пароль и отсутствующий email дают одинаковый `401` с `invalid email or password`. Невалидный JSON — `400`.

## Аутентификация задач

Каждый запрос к `/api/v1/tasks` и `/api/v1/tasks/{id}` требует:

```http
Authorization: Bearer <access_token>
```

Без токена, с истёкшим или недействительным токеном — `401`, заголовок `WWW-Authenticate: Bearer`. Права определяются по `sub`, клиент не передаёт `owner_id`. Чужой и отсутствующий ID дают одинаковый `404`, а не `403`, чтобы не раскрывать существование чужой записи.

## Создать задачу

`POST /api/v1/tasks`:

```json
{"title":"Write tests","description":"Check task permissions","status":"todo"}
```

| Поле | Правила |
|---|---|
| `title` | Обязательно; 1–200 байт после обрезки пробельных краёв |
| `description` | До 10000 байт, по умолчанию `""`; хранится без trim |
| `status` | `todo`, `in_progress`, `done`; при создании пропуск/пустая строка означают `todo` |

`201 Created`: объект задачи и `Location: /api/v1/tasks/<id>`.

Поля задачи: `id`, `owner_id`, `title`, `description`, `status`, `created_at`, `updated_at`. ID и даты назначает PostgreSQL. Нельзя указать другой `owner_id`, ID или время: эти поля неизвестны в теле запроса и дают `400`.

## Получить задачу

`GET /api/v1/tasks/{id}` — `200` с объектом задачи или `404`.

`id` должен быть положительным int64; неверный формат — `400`.

## Список задач

`GET /api/v1/tasks?status=done&limit=20&offset=0`

| Параметр | По умолчанию | Ограничения |
|---|---|---|
| `status` | Без фильтра | Пустой или один из трёх статусов |
| `limit` | 20 | Целое 1–100 |
| `offset` | 0 | Целое 0–100000 |

Неизвестные и повторяющиеся параметры — `400`. Выборка всегда только по текущему пользователю, сортировка `created_at DESC, id DESC`.

`200 OK`, например для пустого списка:

```json
{"items":[],"limit":20,"offset":0}
```

`items` — массив задач. Поля `total` нет; при необходимости следующей страницы клиент увеличивает `offset`. При конкурентных изменениях offset-пагинация не гарантирует неизменный состав страниц.

## Полностью обновить задачу

`PUT /api/v1/tasks/{id}`:

```json
{"title":"Write tests","description":"Owner permissions tested","status":"done"}
```

`title` и `status` обязательны; пропущенный `description` заменяет прежний текст пустой строкой. Это **не PATCH**. Любой из трёх статусов можно сменить на любой другой; ограниченного workflow нет. `created_at` сохраняется, `updated_at` меняется. При одновременных обновлениях остаётся последняя записанная версия.

`200 OK` — обновлённая задача; `400` — невалидный ввод; `404` — своей задачи с таким ID нет.

## Удалить задачу

`DELETE /api/v1/tasks/{id}` — `204 No Content`, без тела. Удаление физическое. Повторное удаление или чужая задача — `404`.

## Состояние сервиса

| Маршрут | Успех | Смысл |
|---|---|---|
| `GET /healthz` | `200`, `{"status":"ok"}` | HTTP-сервер отвечает |
| `GET /readyz` | `200`, `{"status":"ready"}` | PostgreSQL отвечает на Ping |

Проверки без токена. При недоступной БД `/readyz` возвращает `503`. Схема проверяется при старте приложения; readiness не проводит аудит наличия каждой таблицы.

## Прочие ошибки

- `413` — тело больше 64 KiB.
- `500` — внутренняя ошибка; детали записываются в лог, SQL и ошибки драйвера клиенту не выдаются.
- `503` — контекст запроса отменён/истёк либо БД недоступна в readiness. Не каждая ошибка БД классифицируется как `503`: остальные внутренние ошибки дают `500`.

Не повторяйте слепо `POST` после сетевой ошибки: сервер мог успеть сохранить запись. Ключи идемпотентности в текущей версии не реализованы.
