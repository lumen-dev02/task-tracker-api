# Архитектура и решения

## Слои

```text
net/http -> httpapi -> service -> store.Postgres -> PostgreSQL
               |
          auth.Tokens
```

`httpapi` декодирует HTTP, проверяет JWT, извлекает ID пользователя и переводит ошибки в статусы. `service` нормализует вход, проверяет правила полей и работает с паролями. `store` содержит параметризованные SQL-запросы. Общие структуры находятся в `model`.

Интерфейс `Repository` объявлен в использующем его service-слое, чтобы unit-тесты не требовали БД. Рабочая реализация только одна — PostgreSQL. Интерфейсы для каждого типа, универсальный CRUD и отдельный use-case на каждый метод здесь не дают заметной пользы.

## Модель данных

- `users`: identity ID, уникальный нормализованный email, имя, bcrypt hash, время создания.
- `tasks`: identity ID, владелец с FK на пользователя, заголовок, описание, статус, время создания/обновления.

Статусы хранятся как `TEXT` с `CHECK`: для трёх фиксированных значений отдельный справочник и join не нужны. Ограничения длины и статуса продублированы в БД, чтобы ошибки обходного SQL не нарушали инварианты. FK не допускает задачу без владельца; при удалении пользователя через административный SQL задачи удалятся каскадно. API удаления пользователя нет.

Два индекса соответствуют двум сценариям списка: `(owner_id, created_at DESC, id DESC)` и `(owner_id, status, created_at DESC, id DESC)`. Второй позволяет фильтровать статус без потери порядка. Это выбор под запросы, а не утверждение о замеренной производительности.

Одиночные изменения выполняются одним SQL statement; отдельная ручная транзакция вокруг единственного `INSERT` или `UPDATE` не нужна. Конкурентную регистрацию email разрешает `UNIQUE`, а не предварительная проверка с гонкой между SELECT и INSERT. Нарушение уникальности переводится в `409`.

## Проверка доступа

JWT содержит числовой ID пользователя в `sub`, срок действия и фиксированные issuer/audience. Используется общий случайный секрет HS256; алгоритм не выбирается по непроверенному токену. Пароли не кладутся в claims. Токены не логируются и не хранятся в БД.

Владелец берётся только из проверенного `sub`. Каждый запрос чтения, изменения и удаления содержит `WHERE owner_id = $1 AND id = $2`; списки тоже ограничены владельцем. Это исключает окно между отдельной проверкой прав и записью. Чужие ID не отличаются от отсутствующих (`404`). Случайность или непредсказуемость ID не используется как защита.

Авторизация не требует загрузки пользователя для каждого запроса. Обратная сторона: нет немедленного отзыва токена. Административное удаление пользователя не аннулирует подпись уже выданного JWT; в API нет управления удалением или блокировкой аккаунта. Для таких сценариев понадобится проверка состояния аккаунта/сессии и пересмотр политики токенов.

## Пароли и HTTP

Пароли хешируются bcrypt с cost 10 и случайной солью библиотеки. Вход с неизвестным email выполняет сравнение с заранее созданным dummy hash, чтобы убрать очевидную разницу «нет bcrypt / есть bcrypt». Это не обещание одинакового времени всех ответов и не замена защите от перебора.

Тело ограничено 64 KiB, заголовки — настройкой HTTP-сервера. Неизвестные JSON-поля запрещены: клиент не может добавить `owner_id`. JSON декодируется стандартным `encoding/json`: отдельного запрета повторяющихся JSON-ключей нет, действует поведение стандартного декодера. Дубли query-параметров списков, напротив, отклоняются явно.

Контекст запроса ограничен пятью секундами и передаётся в БД. Тяжёлый bcrypt нельзя прервать этим контекстом, поэтому при публичном размещении нужны лимиты запросов и одновременной аутентификации. Приложение не объявляется production-ready.

## Миграция и запуск

Начальный SQL встроен в бинарник через `go:embed`. Режим `-migrate` берёт транзакционную advisory lock, проверяет таблицу версий и применяет схему с записью версии в одной транзакции. Ошибка откатывает всю миграцию; параллельный runner ждёт lock и затем видит уже применённую версию. Блокировка действует на runner, использующий тот же протокол, не на произвольные ручные DDL.

Compose запускает миграцию отдельным одноразовым сервисом после healthcheck БД. API стартует только после её успеха. Обычный запуск проверяет версию схемы, но не меняет её сам. Runner намеренно ограничен миграцией `001`; автоматического отката нет.

По `SIGINT`/`SIGTERM` HTTP закрывает listener и ждёт активные запросы до 10 секунд. Затем закрывается пул БД. Контейнеру выделено 15 секунд на остановку. Если HTTP не уложился в бюджет, соединения закрываются принудительно и процесс выходит с ошибкой.

## Тестирование

Unit-тесты проверяют пароли, JWT, валидацию и HTTP-ошибки. Интеграционные тесты запускают настоящий HTTP-сервер через `httptest`, вызывают API и работают с PostgreSQL через ту же реализацию repository, что и приложение.

Каждый PostgreSQL-тест получает уникальную схему и отдельный `search_path`; очистка удаляет только эту схему. Тестовый URL задаётся явно. Сценарии включают запрет доступа ко всем операциям с чужой задачей, нормализацию/уникальность email, конкурентную регистрацию, фильтры, порядок страниц и транзакционный откат неуспешной миграции.
