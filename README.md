# Task Tracker API

[![CI](https://github.com/lumen-dev02/task-tracker-api/actions/workflows/ci.yml/badge.svg)](https://github.com/lumen-dev02/task-tracker-api/actions/workflows/ci.yml)

Небольшой API для личных задач на Go и PostgreSQL. Регистрируешься, получаешь токен, создаёшь задачи и меняешь их статусы. Каждый пользователь видит только свои записи.

Здесь я сосредоточился на базовых вещах: регистрации, JWT, SQL и проверке доступа. В отличие от [Team Task Manager](https://github.com/lumen-dev02/team-task-manager), здесь нет команд и ролей — задача принадлежит одному пользователю. Поэтому и правила доступа проще: владелец может читать и менять задачу, остальные получают `404`.

## Что работает

- Регистрация с уникальным email и хешированием пароля через bcrypt.
- Вход и JWT access-токен сроком на один час.
- Создание, получение, полное обновление и удаление своих задач.
- Статусы `todo`, `in_progress`, `done`.
- Фильтр по статусу, пагинация `limit`/`offset`, сортировка от новых задач к старым.
- Проверки состояния HTTP-сервера и соединения с БД.
- Ожидание текущих запросов при остановке по `SIGINT`/`SIGTERM`.

## Стек

Go 1.26+, стандартный `net/http`, PostgreSQL 17, `pgx/v5`, `golang-jwt/jwt/v5` и bcrypt. SQL написан вручную. В Compose есть приложение, база и отдельный сервис для применения миграции.

## Быстрый запуск

Понадобятся Git, Docker с Compose v2 и OpenSSL. Для запуска через Docker локальный Go не требуется.

```bash
git clone https://github.com/lumen-dev02/task-tracker-api.git
cd task-tracker-api
cp .env.example .env
openssl rand -hex 32
```

Вставьте результат последней команды в `JWT_SECRET` в `.env`. С шаблонным секретом API не запустится. Пароль PostgreSQL из примера оставляйте только для локальной разработки. При замене удобно взять hex-строку, чтобы не экранировать символы в URL подключения.

```bash
docker compose up --build -d
docker compose ps -a
curl --retry 20 --retry-connrefused --retry-delay 1 --fail http://127.0.0.1:8081/readyz
```

Сначала Compose поднимает PostgreSQL, затем применяет миграцию и запускает API. Контейнер `migrate` после работы должен быть в состоянии `Exited (0)` — это нормально. API доступен на `127.0.0.1:8081`, БД — на `127.0.0.1:55433`. Порты можно изменить в `.env`; по умолчанию оба доступны только локально.

```bash
docker compose logs api migrate
docker compose down
```

`down` останавливает контейнеры и сохраняет данные. Флаг `-v` удаляет volume вместе с базой — не добавляйте его, если данные ещё нужны. Замена пароля в `.env` не меняет пароль в уже созданной базе.

### Запуск приложения без Docker

Понадобятся Go 1.26+ и PostgreSQL. Базу можно оставить в Compose:

```bash
docker compose up -d --wait db
export DATABASE_URL='postgres://tracker:local-development-only@127.0.0.1:55433/tasktracker?sslmode=disable'
export JWT_SECRET="$(openssl rand -hex 32)"
go run ./cmd/api -migrate
go run ./cmd/api
```

Если контейнер API уже занимает порт `8081`, сначала остановите его: `docker compose stop api`. URL выше соответствует исходному `.env.example`; если меняли пароль или порт, обновите его. При запуске через Go приложение само не читает `.env`, нужны переменные окружения.

Режим `-migrate` применяет схему и выходит. Его можно запускать повторно, JWT-секрет ему не нужен. Обычный запуск схему не меняет: без миграции API завершится с ошибкой.

## Попробовать API

```bash
curl --fail-with-body -sS http://127.0.0.1:8081/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"timur@example.com","name":"Timur","password":"local-demo-password"}'

curl --fail-with-body -sS http://127.0.0.1:8081/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"timur@example.com","password":"local-demo-password"}'
```

Скопируйте `access_token` из ответа входа:

```bash
export TOKEN='<access_token>'
curl --fail-with-body -i http://127.0.0.1:8081/api/v1/tasks \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"Write API tests","description":"Check task permissions"}'

# Подставьте id созданной задачи вместо 1.
curl --fail-with-body -sS -X PUT http://127.0.0.1:8081/api/v1/tasks/1 \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"title":"Write API tests","description":"Check task permissions","status":"done"}'

curl --fail-with-body -sS 'http://127.0.0.1:8081/api/v1/tasks?status=done&limit=20&offset=0' \
  -H "Authorization: Bearer $TOKEN"
```

При создании статус по умолчанию — `todo`. В `PUT` нужно передать заголовок и статус; если не передать описание, оно станет пустым. Это полная замена редактируемых полей, не частичное обновление.

| Маршрут | Результат |
|---|---|
| `POST /api/v1/auth/register` | `201`, регистрация |
| `POST /api/v1/auth/login` | `200`, JWT на один час |
| `POST /api/v1/tasks` | `201`, новая задача |
| `GET /api/v1/tasks` | `200`, список своих задач |
| `GET /api/v1/tasks/{id}` | `200`, одна задача |
| `PUT /api/v1/tasks/{id}` | `200`, обновлённая задача |
| `DELETE /api/v1/tasks/{id}` | `204`, без тела |

Все маршруты задач требуют Bearer-токен. Без него будет `401`, для чужой или отсутствующей задачи — `404`. Параметры, форматы ответов и остальные ошибки описаны в [справочнике API](docs/api.md).

### Повторяемый сценарий с двумя пользователями

Нужны запущенный API, `curl`, `jq` и `openssl`:

```bash
bash scripts/demo.sh
# Другой адрес:
BASE_URL=http://127.0.0.1:8082 bash scripts/demo.sh
```

Скрипт создаёт двух пользователей, добавляет задачу первому и проверяет, что второй не может её прочитать. Затем переводит задачу в `done`. Аккаунты и задача остаются в БД, пароли и токены в терминал не выводятся.

## Конфигурация

| Переменная приложения | Значение по умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | Обязательна | Подключение PostgreSQL |
| `JWT_SECRET` | Обязательна для API | Не менее 32 байт, не шаблон; используйте случайное значение |
| `HTTP_ADDR` | `127.0.0.1:8081` | Адрес HTTP-сервера; внутри Compose — `:8080` |

В `.env` для Compose также доступны `APP_PORT`, `DB_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`. Это настройки Compose, а не отдельные настройки Go-приложения. Не публикуйте `.env` и JWT-секрет.

Лимиты имени, заголовка и описания считаются в байтах UTF-8, не в символах. Например, кириллица занимает больше одного байта на букву. Точные ограничения — в справочнике API.

## Проверки

```bash
go test -race -count=1 -timeout=120s ./...
go vet ./...
go build -o bin/api ./cmd/api
```

Без `TEST_DATABASE_URL` интеграционные тесты пропускаются. Для полного прогона нужна работающая БД. Например, для локального Compose:

```bash
TEST_DATABASE_URL='postgres://tracker:local-development-only@127.0.0.1:55433/tasktracker?sslmode=disable' \
  go test -race -count=1 -timeout=120s ./...
```

Тесты создают отдельные схемы и удаляют их после выполнения. Пользователю БД нужно право `CREATE`. Таблицы приложения не очищаются, но для тестов всё равно лучше выделить отдельную базу. Также есть `make test`, `make integration`, `make vet` и `make build`; для `integration` нужно явно задать URL.

В тестах есть регистрация, вход, CRUD, фильтры и пагинация. Отдельно проверяются попытки прочитать, изменить и удалить чужую задачу, регистрация одного email одновременно из двух запросов и откат неуспешной миграции. GitHub Actions запускает тесты с PostgreSQL и race detector, `go vet` и собирает Docker-образ.

## Структура и решения

```text
cmd/api/           конфигурация запуска, подключение БД, HTTP и сигналы
internal/auth/     выпуск и проверка JWT
internal/config/   чтение переменных окружения
internal/httpapi/  маршруты, JSON, аутентификация и HTTP-ошибки
internal/model/    структуры данных
internal/service/  валидация, пароли, сценарии работы с задачами
internal/store/    SQL-запросы PostgreSQL
internal/testutil/ изолированные схемы для интеграционных тестов
migrations/        SQL и runner начальной миграции
scripts/           демонстрационный сценарий
```

Владелец берётся только из проверенного JWT. Передать `owner_id` в теле нельзя: неизвестное поле даст `400`. В SQL чтение, обновление и удаление сразу ограничены владельцем, без отдельного запроса «а можно ли этому пользователю?». Списки тоже содержат только его задачи.

Валидация находится в `service`, SQL — в `store`. Интерфейс репозитория нужен для unit-тестов без БД; настоящие запросы и права проверяются интеграционными тестами. Статусы и длины полей дополнительно ограничены в PostgreSQL.

За уникальность email отвечает `UNIQUE` в базе. Если два запроса регистрируют один адрес одновременно, один получает `201`, второй — `409`.

Подробнее о схеме, безопасности и компромиссах: [архитектура](docs/architecture.md).

## Чего пока нет

Совместного доступа, проектов, вложений и уведомлений. Нет refresh-токенов, отзыва JWT, восстановления пароля и подтверждения почты. Ответ `409` при регистрации позволяет узнать, что email занят.

При двух одновременных обновлениях остаётся последняя записанная версия: истории и защиты от затирания изменений здесь нет. Offset-пагинация может смещаться при добавлении или удалении задач; общего `total` и квоты задач на пользователя тоже нет.

Runner умеет применять только начальную миграцию. Для следующего изменения схемы нужен новый версионный шаг или готовый инструмент миграций; переписывать уже применённый SQL нельзя.

API рассчитан на локальный запуск. Перед публикацией понадобятся HTTPS, ограничение запросов — особенно к регистрации и входу с затратным bcrypt, — отдельные секреты и резервные копии.
